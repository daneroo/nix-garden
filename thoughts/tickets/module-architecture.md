## Current architecture

`flake.nix` (129 lines) builds everything from two `let` values:

- `hostModules name` returns the ordered module list for a host: `hosts/<name>`
  (which imports its `hardware-configuration.nix`), `modules/e2e.nix`,
  `modules/paperwm.nix`, `modules/vm-variant.nix`, and an inline shared block
  (bootstrap packages, `configurationRevision`, systemd-boot retention,
  `programs.nh`, Tailscale, Brave MIME defaults).
- `mkHost` calls
  `nixpkgs.lib.nixosSystem { system; modules = hostModules name; }` for
  `hosts = [ "hardy" "gauss" ]`.
- `packages.x86_64-linux` calls `tests/lib.nix` once per host with
  `{ hostName; hostModules = hostModules hostName; vmLayer = ./modules/vm-layer.nix; }`
  and adds `test-report`.
- A flake-level `pkgs = import nixpkgs { system; config.allowUnfree = true; }`
  feeds both the bootstrap package list and the test library.

Files today and their roles:

- `hosts/hardy/default.nix` (295 lines) and `hosts/gauss/default.nix` (334
  lines): near-identical full host configurations; see Duplication.
- `hosts/*/hardware-configuration.nix`: generated by `nixos-generate-config`,
  import `not-detected.nix`, set `nixpkgs.hostPlatform` with `mkDefault`.
  Untouched by this work.
- `modules/e2e.nix`: ydotool injection daemon on real hosts, before keyd.
- `modules/paperwm.nix`: PaperWM extension package and the system-owned toggle
  with its Vicinae script surface.
- `modules/vm-layer.nix`: VM-only testability layer (autologin, fixture
  password, no idle blanking, VM sizing). Must never reach a real host.
- `modules/vm-variant.nix`: hands `vm-layer.nix` to `virtualisation.vmVariant`
  so `nixos-rebuild build-vm` and `just e2e-vm --no-test` get it.
- `tests/lib.nix`: `runNixOSTest` wrapper;
  `nodes.machine.imports = hostModules ++ [ vmLayer ]` plus instrumentation;
  adds a `keyboards.vm` keyd declaration when `hostName == "hardy"`.

Consumers of flake outputs outside `flake.nix`: `scripts/e2e-vm.sh`
(`.#test-desktop-$host.driver`, `.driverInteractive`,
`.#nixosConfigurations.$host.config.system.build.vm`, `.#test-report`),
`scripts/bootstrap-apply.sh` and the `Justfile` (`.#<hostname>`),
`scripts/omarchy-vm.sh` (`--inputs-from` the repository, so it needs the
`nixpkgs` input name to survive), `scripts/current-state.sh`
(`system.configurationRevision` and the root `nixpkgs` lock node).

Host-specific, and therefore genuine exceptions:

  a dedicated `keyd` group, `CAP_SETGID` added to the unit, and `daniel` in that

  `users.users.daniel.linger = true`.
- Hostname, and by convention `stateVersion`, stay host-local.

Settings that look shared but encode host behavior or hidden coupling:

- The Ghostty config files differ only in comments, so their store paths differ
  per host. Unifying them changes one host's `L+` target; the effective
  configuration is identical and the plan records this as an expected
  difference.
- keyd's `"alt+shift" = { }` layer is declared per keyboard, so it belongs to
  each host's keyboard declaration, not to the shared keyd feature. The reason
  it exists (the application mapper cannot bind a composite layer dynamically)
  is shared knowledge and moves to the feature's comment.
- hardy's keyd ids include the E2E injection device; `tests/lib.nix` adds a
  hardy-only `keyboards.vm` for the VM keyboard. The E2E feature and hardy's
  keyd exception reference each other and must say so.
- `programs.nh.flake = "/home/daniel/nix-garden"` and
  `polkitPolicyOwners = [ "daniel" ]` couple features to the user. That is
  acceptable for a single-user fleet and is documented, not abstracted.
- `nixpkgs.config.allowUnfree` is set in every host and in the flake's own
  `pkgs`; both stay, one in a feature and one in `perSystem`.

## Merge semantics that constrain feature ownership

- `programs.dconf.profiles.user.databases` compiles each list element into its
  own database and lookup is first-wins per key in profile order (nixpkgs
  `programs/dconf.nix`). Splitting settings across features is safe only with
  disjoint key paths. The VM layer and the test node already rely on this, so it
  is existing repository practice. `org/gnome/shell` (enabled extensions,
  favorites, log-out visibility) is the one key group several features care
  about; it gets exactly one owner.
- `systemd.tmpfiles.rules`: systemd-tmpfiles creates a prefix path before any
  suffix path regardless of line order, creates missing parents implicitly as
  root `0755`, and errors on conflicting entries for one path (tmpfiles.d(5)).
  Each path therefore needs one owner, parent directories included, and then
  features may declare their own lines.
- List-valued options concatenate in module-system order. A module's own
  definitions merge after its imports, and the top-level order is not preserved
  literally (probed with `lib.evalModules` on nixpkgs `2c423e0`). Reordering
  `environment.systemPackages` changes the `system-path` derivation without
  changing behavior; the fingerprint's semantic section is order-independent so
  such changes are visible as derivation-only diffs.

## Upstream facts (checked 2026-09-18)

- flake-parts `main` is `31729ca` (2026-09-03). Its only input is `nixpkgs-lib`;
  `inputs.flake-parts.inputs.nixpkgs-lib.follows = "nixpkgs"` keeps the lock at
  one new node.
- `flake.nixosModules` is `lazyAttrsOf deferredModule` whose `apply` wraps each
  entry with `_class = "nixos"` and a `_file` naming the attribute
  (`modules/nixosModules.nix`). `nix flake show` lists each entry as a NixOS
  module and `nix flake check` accepts the output silently.
- `flake.modules.<class>.<name>` (`extras/modules.nix`, imported through
  `flake-parts.flakeModules.modules`) is the newer class-typed option. A scratch
  probe on `galois` showed Nix 2.35 reporting the resulting `modules` output as
  "unknown flake output" in `nix flake show` and "unchecked" in every
  `nix flake check`, which is the repository's mandatory gate. It buys class
  checking across NixOS, Home Manager, and Darwin, none of which this repository
  mixes.
- import-tree is now `github:denful/import-tree` (the owner renamed). It imports
  every `.nix` file under a directory except paths containing `/_`, and composes
  as `mkFlake { inherit inputs; } (inputs.import-tree ./modules)`.
- The Dendritic pattern (`mightyiam/dendritic`) says every non-entry file is a
  module of one top-level configuration, at a path that names its feature, and
  that feature files may contribute to several configuration classes. It
  presents flake-parts as the common vehicle and import-tree as optional.
- flake-parts `perSystem` defaults `pkgs` to `legacyPackages`, without
  `allowUnfree`; `_module.args.pkgs` is the documented override.

## Decisions

Settled with Daniel in a grilling session on 2026-09-18.

- flake-parts composes the flake; `systems = [ "x86_64-linux" ]` only, because
  no output is indexed by another system today. Adding `aarch64-darwin` belongs
  to `nix-formatting`.
- Features are published through the newer `flake.modules.nixos.<name>` option
  (`flake-parts.flakeModules.modules`), Daniel's preference for its class typing
  and its alignment with the Dendritic examples he will read. The cost is one
  cosmetic line per `nix flake check` ("unchecked: modules") and that
  `nix flake show` does not list features;
  `nix eval .#modules.nixos --apply builtins.attrNames` does.
  `flake.nixosModules` was the alternative and is not used, to keep one
  mechanism.
- import-tree (`github:denful/import-tree`) auto-imports everything under
  `modules/`. Daniel chose full Dendritic wiring over explicit index files. The
  tradeoff, accepted: no file lists what exists, a stray `.nix` under `modules/`
  is live configuration, and files not ready must carry a leading underscore.
  The aspect directories and one-feature-per-file rule carry the discoverability
  instead. Hosts stay explicit: `hosts/default.nix` lists the machines, because
  the generated `hardware-configuration.nix` files must not be auto-imported and
  an explicit inventory was a stated goal.
- Self-registering aspects, Dendritic style: each feature file defines its named
  module and adds it to an aspect. Three aspects now: `base` (platform),
  `desktop` (compositor-agnostic applications and input), `gnome` (the session
  itself). Daniel expects the fleet to grow and to run more than one desktop
  (GNOME now, Hyprland or Niri later), so the GNOME-specific pieces are kept out
  of `desktop` from the start; a second desktop becomes a sibling aspect.
  Per-feature names stay so a host can cherry-pick.
- The GNOME dconf database is split by owner with disjoint keys, and the session
  feature adds one `assertions` entry that fails evaluation if two databases
  define the same key path. `org/gnome/shell` belongs to the session feature and
  names the extensions other features install.
- The tmpfiles stopgap stays a stopgap. `user-daniel` owns the XDG skeleton
  directories, and each feature owns the subdirectory and `L+` lines for its own
  files. `home-config-ownership` still deletes all of it later.
- The bootstrap package list stays one list (`cli-baseline`), including Ghostty
  and Brave; the Ghostty and Brave features own configuration, not packages.
- `nixosSystem` keeps receiving `system = "x86_64-linux"`; hardware files keep
  `nixpkgs.hostPlatform`.
- `perSystem` sets
  `_module.args.pkgs = import inputs.nixpkgs { inherit system; config.allowUnfree = true; }`,
  reproducing the current flake-level `pkgs`.
- `test-desktop` stays as the alias it is. Removing it needs Daniel's explicit
  approval and is not part of this refactor.
- No Home Manager, no wrapper-manager, no overlays, no partitions, no
  `nix-formatting` work. The flake-parts entry makes a later `formatter` output
  a one-line addition, which is the only interaction.
- Execution harness: the executor on `gauss` runs Claude Code from current
  nixpkgs (`2.1.272` on `nixos-unstable` as of 2026-09-16) with
  `NIXPKGS_ALLOW_UNFREE=1 nix run --impure github:NixOS/nixpkgs/nixos-unstable#claude-code`.
  A fleet update stays a separate item; Daniel said either path is fine as long
  as the model he wants is available.
- Daniel set the bar: a working system and a better design, not byte-identical
  derivations; the hosts are early proof-of-concept desktops and the work is on
  a branch. The gates are `just check` everywhere, `just plan` on both NixOS
  hosts, and the VM suites for both hosts. The fingerprint script's
  order-independent `semantic` section is kept as a cheap check that nothing was
  dropped by accident; derivation paths are informational. Stage 0 records a
  fresh VM baseline because the last recorded runs (2026-07-30) predate the
  2026-08-23 nixpkgs bump.
- Handoff: the planning commit is pushed to `main`; the branch is created and
  pushed from `gauss`.
